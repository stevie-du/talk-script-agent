# 技能包系统方案（可载入第三方包）

> 2026-09-23 立项。目标：让 talk-script-agent 从「内置 N 个行业包」变成
> **可载入技能包的中立平台** —— 用户自己导入第三方包，许可关系在用户与
> 包作者之间；软件本身永不预装、永不推荐、永不开官方市场。
>
> **结论先行：地基已有约 80%，缺的是「导入层」与「来源区分」，不需要
> 新包格式** —— 现有的 `packs/<name>/` 目录就是技能包（见下 §2）。

---

## 2. 技能包格式定义：复用 pack，不造新格式

一个技能包 = 一个目录，`pack.yaml` 为清单。新增三个**可选**字段
（老包不写也能加载，默认值兜底）：

```yaml
name: elevator              # 已有：目录名即身份，唯一键
version: 1                  # 已有：int，升级比对用
# ── 以下为技能包化新增（可选）──
pack_api: 1                 # 技能包格式版本。未来格式不兼容时引擎拒绝加载并说明
source:                     # 来源声明（展示用，不强制）
  author: ""                # 作者/组织
  homepage: ""              # 项目页/联系方式
  license: ""               # 许可证（MIT / Apache-2.0 / MIT-NC …）—— **界面展示，提醒用户自审**
```

设计原则：
- **格式即现有 pack**，零迁移成本；第三方作者看 `packs/elevator/` 就能学着写
- `license` 只是展示字段，引擎不做许可校验（校验不了，也不该由我们裁决）——
  但界面要显示，让用户自己看见他装的是什么
- 目录名（`name`）是身份：同名目录 = 同一个包的替换/升级

## 3. 加载（发现与优先级）

```
加载源（优先级从高到低）：
  1. 用户目录 %APPDATA%\TalkScript\packs\<name>/     ← 第三方导入的落在这里
  2. 安装目录内置包（仅播种用，不进列表）
```

- 同名冲突：**用户目录赢**（用户自己放的覆盖播种的内置版），并在列表上标
  “已覆盖内置版 v1”
- 每次启动扫目录（现有行为）；**不缓存包列表到设置里**——目录是唯一事实源，
  缓存会和“用户刚删了目录”打架
- 坏包三处理：列表留着 + `pack_error` 摊出 + 生成时 `PackBrokenError` 409
  （现有纪律，原样继承）

## 4. 导入与卸载（本方案的主体工程）

### 4.1 导入流程

```
用户选 zip
  → ① 预检（解压前）：大小 ≤ 20MB、条目数 ≤ 500、扩展名白名单
                     （.yaml/.md/.txt/.json + 目录；拒绝 .py/.exe/.sh/.bat/.js）
  → ② 解压到临时目录，**校验 manifest**：pack.yaml 存在、可解析、
     name/version 合规、pack_api ≤ 引擎支持的版本
  → ③ 结构校验：必需文件存在（skill.yaml；banwords 指向的文件存在——
                     引用不存在的文件 = 静默失效，必须拒）
  → ④ 原子落盘：临时目录整体 move 进 packs/<name>/（先删旧同名 =
                     升级；move 失败不留半份）
  → ⑤ 刷新列表 + 告诉用户“已导入 X（author / license / version）”
```

### 4.2 卸载

- 删 packs/<name>/ 整个目录。**内置播种的包删除前要警告**（“这是内置包，
  下次启动会被重新播种”）——或者更简单：内置包不提供卸载，只提供
  “恢复默认”（重新播种）
- 卸载后**明说**成功/失败（删不掉 = 权限/占用，摊到界面）

### 4.3 安全边界（第三方包 = 不可信输入，逐条对应威胁）

| 威胁 | 防线 |
|---|---|
| Zip Slip（`../` 写出 packs 外） | 解压逐条目校验解析路径仍在目标内（现有 `knowledge.py:698` 同款思路要在解压层再做一次） |
| 可执行文件走私 | 扩展名白名单（§4.1①），`.py/.exe/.sh` 一律拒 |
| 包超大塞满磁盘 | 20MB / 500 条目上限 |
| 引用外部文件（`../secret.md`、`C:\...`） | 加载侧已有 `../..` 防护；导入侧结构校验时把 yaml 里的相对路径全部解析确认不逃逸 |
| manifest 不兼容 | `pack_api` 版本闸（拒绝并说明，不静默降级加载） |
| 包坏了但看不出 | 继承现有 `pack_error` 可见化 + 导入时③结构校验把“引用不存在的文件”拦在导入前 |

## 5. 使用（生成链路怎么吃技能包）

**零改动**——现有链路本来就全走 `Pack(root_for_packs, name)`：参数条读
`pack.yaml.params`、提示词读 `skill.yaml`、tell 读 `ai_tells.yaml`、
合规读 `banwords.yaml`。导入的包和内置包在生成链路上**完全同构**，
不需要任何“第三方包特殊路径”。

界面侧只加一处：包下拉里每个选项带来源徽标（内置 / 导入 · author · license），
让用户始终看得见自己用的是谁的东西。

## 6. 管理 UI（设置页「技能包」区）

```
┌ 技能包 ─────────────────────────────────────┐
│ [导入技能包(zip)]   目录：%APPDATA%\...\packs │
│                                               │
│ ● 电梯        v1  内置                        │
│ ● 电梯·自定义  v2  导入 · 张三 · MIT    [卸载] │
│ ● 某社区包    v1  导入 · 未知作者 · MIT-NC ⚠  │
│ ● 坏包        —   导入 · pack_error: …  [详情]│
└───────────────────────────────────────────────┘
```

要点：license 原样展示（MIT-NC 就显示 MIT-NC，我们不替用户裁决但绝不替他
隐藏）；`⚠` 只是提示“这个许可证限制商用，自审”，不是我们的判断。

## 8. 与成熟方案的对照（为什么够用）

| 方案 | 机制 | 我们借鉴/不借鉴 |
|---|---|---|
| VS Code 扩展 | 市场 + manifest + 沙箱（扩展宿主隔离） | 借鉴 manifest；**不**做沙箱（我们的包是纯数据/提示词，无代码执行——白名单已从根上禁掉可执行文件） |
| Obsidian 插件 | vault 目录即插件目录，手动放/市场 | **最像我们**：目录即技能，手动导入是正当用法 |
| Claude/WorkBuddy Skills | SKILL.md + frontmatter + 脚本目录 | 我们的 skill.yaml/patterns 已是同构；不引入脚本执行 |
| npm/pip | 注册表 + 语义版本 + 依赖解析 | 不学前两者：不做中心市场（红线：不推荐、不背书），版本只用于同名升级比对 |

## 9. 红线（本方案的宪法）

1. **不预装、不推荐、不开官方市场**——平台中立性是许可证风险转移的前提
2. **包内不许有可执行内容**——白名单从导入层禁到根
3. **坏包永远可见**——导入前拦、列表上标、生成时报错，三处都不能静默
4. **license 展示但不裁决**——用户自审，我们不背书也不隐藏
