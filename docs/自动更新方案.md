# TalkScript 自动更新方案

> 2026-09-23 出稿，**后经四轮独立复审修订**（修订记录见 §14；代码未动，本文只定方案）。
> 评审通过后按 §13 落地。
>
> 三条取舍基准（用户原话「速度快，性能高，易于维护」）：
> 1. **快** —— 更新下载走差分，典型几 MB；检查是一次 KB 级 GET；不碰冷启动。
> 2. **性能高** —— 无长连接、无轮询风暴、下载在后台；常驻成本 = 6 小时一次 KB 级请求。
> 3. **易于维护** —— 配置只有「一个更新地址」；版本号仍只有 `desktop/package.json` 一处；
>    发布动作收敛成一条命令；不引入「安装包之外的第二份更新真相」。

## 1. 结论速览

| 问题 | 结论 |
|---|---|
| 更新逻辑 | **拉取式**：启动后（延迟 15s）GET 一次版本信息，比本地新 → 后台差分下载 → 下载完即就绪，**退出应用时静默安装**（装完不自动拉起，用户下次自己开）。也支持用户点「立即重启」当场装并自动重启。装前校验 sha512（§3.1） |
| 要推送吗 | **不要**。没有任何服务端主动通道，全部「通信」就是客户端一次 GET |
| 要联网吗 | **要**，但联的是自己的 Linux 服务器；**没配更新地址时一次请求都不发**（不是静默失败，是整体关闭） |
| 入口 | ① 自动：启动一次 + 每 6 小时一次；② 手动：设置 → 关于与更新 → 「检查更新」按钮 |
| 全量 / 增量 | **增量（blockmap 差分）**。版本间不变的字节（内嵌 Python 运行时约 40 MB、Electron、行业包…）差分时全部命中，典型更新只有几 MB |
| 代码签名 | **暂不签**。`latest.yml` 自带 sha512 保完整性；HTTPS 是底线（§12.1） |
| 新增依赖 | `electron-updater`（运行时依赖，会进 app.asar；**不是 devDependencies**） |
| 新增文件 | `desktop/updater-core.js`（纯逻辑，可单测）+ `updater-core.test.js` + `renderer/js/about.js` + `desktop/scripts/publish-update.mjs` + `desktop/scripts/serve-update.mjs`（冒烟专用 Range 服务器） |

形态：**electron-updater + generic provider + 自建静态托管**。客户端不认识「你的服务器是什么系统」，
它只认一个 HTTP(S) 地址；Linux + nginx/Caddy 是最常见搭配。

## 2. 为什么选 electron-updater，不手写

| | electron-updater | 手写（GET 版本号 → 下载 → spawn 安装器） |
|---|---|---|
| 差分下载 | 内置（blockmap，自动） | 要自己实现分块比对 + Range 请求 |
| 完整性校验 | 内置（latest.yml 的 sha512，下载完即校验，不过关不安装） | 要自己对 |
| 版本比较 | 内置（语义化版本） | 要自己写 |
| 安装编排 | 内置（退出时静默装 / 立即重启装）。**v6 没有「下次启动装」**（onNextLaunch 是 v7 API，stable 尚不存在），本文按 v6 写（§3.1） | 要自己拼 NSIS 参数、处理「装着呢应用还开着」 |
| 失败可观测性 | 事件齐全（error / download-progress / update-downloaded…） | 要自己埋 |
| 维护成本 | 一个依赖，跟 electron-builder 同生态 | 长期自己养 |

手写唯一的优势是「不引依赖」，但上面六行没有一行是省事的。**引一个依赖换六种边界情况，
符合「易于维护」。**

⚠ **版本配对是前置条件**（§12.2 单独列了风险）：electron-updater 与 electron-builder 的版本
要对上——`latest.yml` 的元数据格式随 electron-builder 大版本变（官方 compatibility 一节：
builder ≥27 默认生成新版 `files[]` 格式），版本错配的表现是「构建一切正常、客户端永远
检查不到更新且报错难懂」。当前锁 `electron-builder ^25.1.8`（<27，旧版 `files[]`），该风险
暂不激活；落地第 2 步就是确认这一对。

## 3. 更新逻辑（时序与状态机）

### 3.1 正常路径（按 electron-updater **v6** 写——stable 只有 v6）

```
应用启动 → 引擎起来 → 窗口出现 →（延迟 15s，不抢冷启动）
   └→ GET https://<你的服务器>/talkscript/latest.yml     ← 一次 KB 级请求
        ├─ 版本 ≤ 本地            → 无事发生（仅日志一行）
        ├─ 版本 > 本地            → 后台差分下载（blockmap，Range 请求）
        │     └─ 下载完（校验 sha512过关）→ 更新就绪 + 通知「新版本已下载」
        │           ├─ 用户点「立即重启」→ quitAndInstall(isSilent, isForceRunAfter) → 装完自动拉起，即新版本
        │           └─ 用户点「稍后」/ 没理 → 退出应用时静默 spawn 安装器（仅 exitCode 0 时；装完不自动拉起）
        └─ 请求失败 / 404 / 解析失败 → 日志 + 设置页状态行留痕（§3.3）
```

运行期间每 6 小时重复一次检查（定时器，不是轮询——两次检查之间零请求）。

⚠ **先定版本，再写代码**（2026-09-24 实核 npm dist-tags）：`latest` = **6.8.9**（2026-06-05 发布），
`next` = 7.0.0-**alpha**.7 且自 6 月停留至今——**v7 stable 不存在，`npm i electron-updater`
装到的就是 6.8.9**。v6 与 electron-builder 25 正是配套一代（§12.2），本文全部按 v6 API 写。

**v6 的安装语义（`autoInstallOnAppQuit`，默认 true）**：

- 下载完成即校验 sha512（不过关 → error 事件、清缓存、不安装），安装包留在 updater 缓存目录
  （`<userData>/../<app>-updater/pending`，即 `DownloadedUpdateHelper.cacheDirForPendingUpdate`）；
- 下载完成的同时挂上 `app.onQuit` handler（`BaseUpdater.addQuitHandler`）：
  **退出应用且 exitCode = 0 时**，静默 spawn 该安装包（`install(true, false)`——静默、装完**不**
  自动拉起，用户下次自己开）。exitCode ≠ 0（崩溃/异常退出）不装，留给下次；
- 「立即重启」= `quitAndInstall(isSilent=true, isForceRunAfter=true)`：静默装 + 装完自动拉起，
  用户明确点了按钮，不需要二次确认（§4.2 路径 2）。

**为什么不照抄 v7 的 `onNextLaunch`**（原初审稿的默认路径，已按现实推翻）：

- `autoInstallEvent` 是 v7 才有的 API，6.8.9 里**不存在**——照 v7 文档写代码，落地第 2 步
  一装包就发现属性是 undefined，静默失效（正是本项目最反对的失败形态）；
- v6 想手工拼「下次启动装」：需要自己读 updater 的 pending 缓存、自己校验、自己 spawn——
  全是 `@private` 面（`DownloadedUpdateHelper` 没有公开的「取回已下载更新」入口，
  `validateDownloadedPath` 只在下载流程内被调用）。这就是「手写安装编排」，
  与 §2「引一个依赖换六种边界情况」的初衷相悖；
- v6「退出时 spawn」的真实风险比想象小，且**不会半安装**：NSIS 安装器是事务性的，
  在 spawn→安装完的秒级窗口被关机/注销杀死，结果是**本次没装上**（应用仍是旧版、
  照常启动），下次退出再装——不是「应用留在半安装状态」；且只有 exitCode 0 才触发。

**v7 升级只差一行**：等 v7 出 stable，`autoInstallOnAppQuit` → `autoInstallEvent = "onNextLaunch"`，
客户端其他代码不动（v7 的确切安装时序以出 stable 时的官方文档为准，现在它是 alpha，
不预先写死语义）。这也是把 v6/v7 分叉从「赌默认值」变成「一个开关」的写法。

另一条可见性增益：`autoUpdater.logger` 指向我们自己的日志对象，electron-updater 的
内部调试行也进 `updater.log`——否则它内部为什么没检查到更新，只有它自己知道。

### 3.2 只在打包态启用

- `app.isPackaged` 为假（开发态 `npm start`）→ 整体不启用。这是 electron-updater 的内置行为
  （`isUpdaterActive()`：未打包且未 `forceDevUpdateConfig` 时 `checkForUpdates()` 直接返回
  `null` 并打一行 "Skip checkForUpdates…" 日志），我们的 `initUpdater()` 同样早退；
  手动检查此时要回答的是「**开发模式不检查更新**」，不是「未配置更新地址」（§4.3）；
- portable 版（`TalkScript x.y.z.exe` 单文件）→ 不启用。官方 auto-updatable targets 只列
  NSIS，portable 不在内；检测用 `process.env.PORTABLE_EXECUTABLE_DIR`——模板级铁证：
  electron-builder 的 portable 安装模板 `portable.nsi:77` 在每个 portable 包启动时
  `SetEnvironmentVariable("PORTABLE_EXECUTABLE_DIR", "$EXEDIR")`，不靠口头约定。
  双闸门 + electron-updater 自己的报错兜底。
  便携版用户继续「整个替换文件」这一条路。

### 3.3 失败必须可见（本项目铁律）

自动更新最危险的失败形态是「悄悄不更新」——用户以为在用最新版。所以：

| 失败点 | 去处 |
|---|---|
| 网络不通 / 超时 | `updater.log` + 设置页状态行「上次检查失败：<人话原因>」 |
| 404（地址配错） | 同上；人话化时明确说「更新地址不存在」而不是一句 HTTP 404 |
| latest.yml 解析失败 / sha512 不匹配 | 同上 + **不安装**（electron-updater 默认行为），日志留原文 |
| 下载中断 | 同上；下次检查自然重试，不留半截安装包 |
| 下载的安装包校验失败（sha512 不过关） | 日志 + error 事件；electron-updater 清掉缓存安装包，下次检查重新下，不留半截包 |
| 静默安装失败 | 日志；下次启动版本没变，用户从「关于与更新」能看到当前版本号自行判断 |

日志落 `<数据目录>/logs/updater.log`，**复用 engine.log 的同一套机制**（2 MB 轮转一档、
写前过 `maskSecrets`、流错误不冒未捕获异常）——两个文件同一个 logs 目录，排查时只有一个地方看。
启动时 `engine.log` 里那行 `TalkScript v<版本> 启动` 同时就是「更新是否生效」的记录：
版本号变了即生效，不需要另做一套。

⚠ **更新地址里别放机密**（URL 会原样进日志）。需要「知道路径才能更新」就在路径里放一段随机串，
那已经是非机密；要更强的就在请求头上带认证（见 §6 的 NsisUpdater 实例，支持 `requestHeaders`）
——但那会把凭据写进 package.json，分发即公开，权衡见 §12.3。

## 4. 入口

### 4.1 自动入口（覆盖 95% 场景）

- 启动后 15s 一次；之后每 6h 一次。延迟 15s 的理由：不跟引擎启动、页面加载抢那几百毫秒，
  用户的观感是「应用起来了」，更新检查在后台自己跑。
- `autoDownload = true`：发现新版本就后台下，不打断、不询问——**询问应该发生在「装」的时候，
  不是「下」的时候**。下载完成才通知。

### 4.2 手动入口（设置 → 关于与更新）

设置页现在是三个导航项（生成偏好 / 模型接口 / 行业包）。新增第四节「关于」+ 一个导航项
**「关于与更新」**，严格复刻现有 `.stg-nav-item` 的 DOM 与类。

面板结构：**单列，参照 `#pane-packgen` 的既有形态**（不带 `has-cols` 的单面板先例），
复用现成类，不造新 CSS 除了一个状态行：

```
page-head   「关于与更新」+ 副标题
page-card
  ├ 当前版本        TalkScript 0.2.0（读 app.getVersion()，经 IPC 取，不前端猜）
  ├ 更新状态        #upd-status 状态行（七态，见下）
  └ page-actions   [检查更新]（ghost；检查中禁用并转圈）
```

七态（`#upd-status` 的文案与颜色，**复用 `.st-status` 现成样式**，异常态用 `--warn`）：

| 状态 | 界面表现 |
|---|---|
| idle | 「自动更新已开启 · 启动后每 6 小时检查一次」（**常驻状态**，让「有这个功能」本身可见）。⚠ 实现要点：链路启用时 `initUpdater` **必须主动推一次 idle** —— 状态只在变化时推，不推的话用户打开面板看到的第一条一定是 `checking`，这句文案就成了永不显示的死分支，「有自动更新」在界面上没有任何常驻痕迹 |
| checking | 「正在检查更新…」 |
| uptodate | 「已是最新版本 0.2.0」 |
| available | 「发现新版本 0.2.1」→ 自动转 downloading |
| downloading | 「正在下载更新 47%」（`download-progress` 事件的 `percent`，字节级） |
| downloaded | 「0.2.1 已下载完成，退出 TalkScript 时自动安装」+【立即重启】按钮 |
| error | 「检查更新失败：<原因>」+（手动检查时）「完整日志：…updater.log」 |

「立即重启」有两条路，触发条件不同、都通向 `quitAndInstall`：

1. **自动下载完成时**（用户没坐在设置页前）→ 主进程弹确认框，**默认焦点在「稍后」**
   （cancelId）。理由：重启会丢内存中进行中的生成作业，与现有 `restartEngine` 对话框
   告知的是同一件事，不能让手滑把作业送了。
2. **面板里的【立即重启】按钮**（只在 downloaded 态出现）→ 用户已经坐在设置页、
   明确点了这个按钮，直接装，不再二次确认。

### 4.3 IPC（最小面）

`preload.js` 现在只暴露 `isElectron` / `platform`。加一个受管通道：

```js
// preload.js（contextBridge，sandbox 下 ipcRenderer 可用）
contextBridge.exposeInMainWorld('talkscript', {
  isElectron: true,
  platform: process.platform,
  updater: {
    check: () => ipcRenderer.invoke('updater:check'),           // 手动检查；返回当前状态
    getStatus: () => ipcRenderer.invoke('updater:getStatus'),   // 只读取状态，**不触发检查**
    restart: () => ipcRenderer.invoke('updater:restart'),       // 立即重启（只在 downloaded 态可见）
    onStatus: (cb) => {                                         // 主进程推状态（含自动检查）
      const h = (_e, s) => cb(s);
      ipcRenderer.on('updater:status', h);
      return () => ipcRenderer.removeListener('updater:status', h);
    },
  },
});
```

> **`restart` 与 `getStatus` 是本节两条通道之外的补通道**（实现里已落地，这里补记）：
> - `restart` —— §4.2 路径 2 要求那颗【立即重启】按钮「直接装」，而渲染层碰不到 updater
>   实例（它在主进程）。塞进 `check` 的参数里会让「取状态」与「执行安装」共用一个名字。
> - `getStatus` —— 面板打开时要的是「现在是什么状态」，不是「去查一次」。
>   走 `check` 会在启用态**真的发一次请求**，并把 6h 自动检查的时钟往后推
>   （`runCheck` 的第一件事就是 `updaterLastCheckAt = Date.now()`），于是
>   「每 6 小时一次」实际变成"取决于用户点开面板的频率"，与 §1「两次检查之间零请求」冲突。

主进程 `ipcMain.handle('updater:check')`：手动检查的结果永远必须是可见的，包括「没开」这个
答案，且**三种「没开」文案不同**：

| 情形 | 返回态 | 文案 |
|---|---|---|
| dev 态（`isPackaged` 假） | `disabled` | 「开发模式不检查更新」 |
| portable 态（`PORTABLE_EXECUTABLE_DIR` 在） | `disabled` | 「便携版不支持自动更新，请手动替换文件」 |
| 打包态但没配地址（`resolveFeedUrl` 为 null） | `disabled` | 「未配置更新地址」 |
| 配了地址、检查中 | `checking` | 「正在检查更新…」 |

> 三种「没开」统一返回 `disabled`（不是 `error`）：它们**不是故障**，但都要可见（§3.3）——
> 渲染层对 `disabled` 与 `error` 用同一种警示色、不同的话。判定与文案都在
> `desktop/updater-core.js` 的 `disabledStatus()`，有单测（含 dev 优先于 portable、
> portable 优先于「没配地址」的顺序）。

重复点击不叠加检查：updater 内部对并发 `checkForUpdates()` 复用同一个 promise（日志
"Checking for update (already in progress)"），IPC 层直接透传即可。

## 5. 全量 vs 增量：默认增量；仅「老用户 + 缓存健在」成立，缓存不在自动回退全量

electron-builder 出包时**自动**为 Setup exe 生成 `.blockmap`，electron-updater 默认
差分下载（无需任何配置，把 `.blockmap` 跟 exe 一起放上服务器即可）。

差分原理：客户端拿 **updater 缓存目录里的旧安装包**（上次更新下载后由 `DownloadedUpdateHelper`
留存，差分时以 `cacheDir` 下的旧包为基准）当 diff 基准，只从服务器拉新安装包中与旧包不同的
块。所以：

- 版本间不变的字节差分时**全部命中**——内嵌 Python 运行时（实测 38.7 MB，见 `PACKAGING.md`）、
  Electron 运行时、行业包，只要没动就是一个块都不拉；真正要拉的只有改过的 `app/`、
  `renderer/`、`packs/` 那部分，**典型几 MB**；
- **老用户的第一次自动更新就是增量**——只要上次走过 updater 且缓存还在；服务器上**不需要**
  为差分保留任何旧版本（基准在客户端）；
- 缓存不在（新装机 / 用户清过缓存 / 从没走过 updater 的用户直接装了新版）→ 自动**回退全量
  下载**，不会失败，只是慢一次。所以「第一次就是增量」仅对「老用户 + 缓存健在」成立；
- 只有内嵌运行时本身升级（Python 版本 / 依赖变）才接近全量——那是少数情况，且本来就该全量。

**明确不做「部件级热更」**（只更新 asar / 只更新 renderer）：
引擎代码 `app/` 与渲染层 `renderer/` 都在 asar 之外的 `extraResources` 里，
部件更新覆盖不全；更关键的是它会制造**第二份更新真相**（「安装包是一份、部件补丁是另一份」），
正是本项目一贯要消掉的「同一信息两份表示」。整包差分只有一份真相：安装包。

## 6. 更新地址：配置只有一处，不配就整体关闭

```
渲染层按钮  →  IPC  →  主进程 updater-core.resolveFeedUrl()
                        环境变量 TALKSCRIPT_UPDATE_URL（唯一来源，非空才启用）
                        没有 / 为空 → 自动更新整体关闭，一次网络请求都不发
```

- **运行期只认环境变量**，不读 package.json 的 `build.publish.url`。理由：那份 URL 只是
  **构建期生成 latest.yml 的占位**（见 §9），客户端去读它等于「占位地址也可能被真的请求」。
  将来要正式分发，再把 package.json 加进解析顺序——那是「一次改动 + 一条测试」，不是重构。
- 运行时用**自建 updater 实例**拿地址（官方「instantiating updater directly」的正规做法）：

  ```js
  const { NsisUpdater } = require('electron-updater');
  const updater = new NsisUpdater({ provider: 'generic', url: feedUrl });
  ```

  ⚠ **不要用 `autoUpdater.setFeedURL`**——官方文档原话 "Do not call setFeedURL"。
  自建实例同样支持 `requestHeaders`（将来要请求头认证就有地方放）。
- 地址规范化（去首尾空白、补尾斜杠）在纯函数里做，有单测（§10）。
- 自己机器上启用：`setx TALKSCRIPT_UPDATE_URL "https://你的服务器/talkscript/"`（重启终端/应用后生效）。

## 8. 服务器侧（一次性，约 10 分钟）

```
/var/www/talkscript/
├── latest.yml                          ← electron-builder 自动生成，禁止手写
├── TalkScript Setup 0.2.1.exe
└── TalkScript Setup 0.2.1.exe.blockmap
```

nginx（一段就够；Range 请求静态文件默认支持，差分下载靠它）：

```nginx
location /talkscript/ {
    alias /var/www/talkscript/;
}
```

Caddy（顺带自动签 Let's Encrypt，更省事）：

```
talkscript.example.com {
    root * /var/www/talkscript
    file_server
}
```

- **HTTPS 是底线**：无签名 + 纯 HTTP = 中间人可以给你塞任何安装包。有域名用 Caddy 自动签；
  只有 IP 签不了证书——那是纯局域网场景，风险自担（§12.1）。
- 差分下载**不需要**服务器留旧包（基准在客户端缓存），但**回滚需要上一版安装包**：发错包、
  新包有恶性 bug 时，旧 exe 没了就只能重出一个 96 MB 的包。所以发布脚本默认 `--keep 2`
  （§9 步骤 5），确认无恙后再收紧成 1。
- electron-updater 在主进程用 Node 的 HTTP 栈拉 `latest.yml`，**不涉渲染层 CORS**，无需 CORS 头。
- generic provider 官方明确「不会自动上传，必须手动传」——这正是 §9 发布脚本的存在理由。

## 9. 发布脚本：出包之后一条命令

**前置条件**：`package.json` 配了 `publish`（generic + 占位 URL）才会生成 `latest.yml`
（官方 Quick Setup 第 2、3 步：配 publish → 构建 → 检查 dist 里有 metadata yml）。
generic 不会自动上传，所以「上传」这一步必须由我们的脚本做。

`desktop/scripts/publish-update.mjs`（零依赖，跟 `build-python-runtime.mjs` 一个风格；
Windows 开发机用内置的 `scp`，不依赖 rsync）：

```bash
cd desktop
npm run dist                                  # 产物在 dist/（含 latest.yml 与 blockmap）
node scripts/publish-update.mjs \
  --to  user@你的服务器:/var/www/talkscript \
  --url https://talkscript.example.com/talkscript/
```

脚本做的事（顺序即防线）：

1. **校验产物**：`dist/latest.yml` 存在且其 `version` 与 `package.json` 的 version 一致；
   latest.yml 里列的文件（exe + blockmap）都在 dist/ 里，且逐个**重算 sha512** 与 yml
   记录比对（crypto.createHash，流式读；只比大小拦不住「同长度不同内容」，客户端
   下载后正是拿这个字段校验）。缺一样或对不上就退出，不半上传。
2. **防降级**：GET 线上 `latest.yml`，与本次 version 三分（与 publish-update.mjs
   步骤 2 的实现逐支对齐，2026-09-26 对账——本文早先写的「≥ 就拒绝」少了两个分支）：
   - 线上 version **更高**（cmpVer > 0）→ **拒绝上传**（防止把旧包覆盖上去这种「无声回退」）；
   - **相等** 且文件齐全（逐个 HEAD 200）→ **拒绝重传**：同一 version 两份不同的包，
     客户端缓存会打架；要重发就提升 version 重新出包；
   - **相等** 但缺文件 → 判定「上次上传中断」，**允许补传**（latest.yml 最后传，
     它到了包没到，正是中断的痕迹）；
   - 线上 version 更低，或线上还没有 latest.yml（404）→ 放行。
3. **上传**：`scp` 三个文件（latest.yml / exe / blockmap）。
4. **闭环验证**：再 GET 一次线上 `latest.yml`，断言 version = 本次 version、文件可下载
   （HEAD 200）。上传完必须能回答「线上现在到底是什么版本」。
5. `--keep N`（默认 **2**）：清理服务器上更老的 exe / blockmap，只留最近 N 版。
   默认留 2 是为了回滚——发错包 / 新包有恶性 bug 时，旧 exe 没了就只能重出一个全量包
   （§8）。确认一个版本周期无恙后，再收紧成 1。
6. `--dry-run`：只跑 1、2、4 的检查不动文件。

每一步失败都打印**哪一步、为什么、下一步该怎么办**——与项目现有报错对话框同一条规矩
（末尾给日志/路径，不让人猜）。

## 11. 性能与维护性账

**性能**：

- 冷启动零影响：检查延迟到窗口出现后 15s；`latest.yml` 一次 KB 级 GET，异步，不阻塞任何路径。
- 更新体积：差分（典型几 MB）；且第一次自动更新就享受差分，不需要「先全量下一次」。
- 安装：NSIS `/S` 静默，秒级；安装包**下载完时已校验 sha512**（不过关不安装，§3.1），
  退出应用时才 spawn，不占使用中的时间。安装模式沿用首次安装的选择
  （`nsis.oneClick:false` 带安装模式页，`perMachine` 默认 false）：选 per-user 免 UAC；
  选 per-machine 的静默更新会弹一次 UAC，electron-updater 自动用 elevate.exe 提权重试
  （`NsisUpdater.doInstall` 的 EACCES 兜底路径），装完不自动拉起。
- 常驻：6h 一次 KB 级请求；无 WebSocket、无长连接、无后台驻留下载器。

**维护**：

- 配置只有「一个环境变量」，且运行期只此一个来源（§6）。
- 版本号仍只有 `desktop/package.json` 一个来源（main.js:91 的既有约定不动）。
- 发布动作 = `npm run dist` + `npm run publish:update` 一条命令，防降级与闭环验证都在脚本里。
- 服务器默认只留最近 2 个版本（`--keep 2`，回滚用，§8/§9；观察一个版本周期无恙后可收紧成 1），
  无需版本库、无需数据库、无需 CI（将来想要 CI 也只是把这两条命令搬进 workflow，
  不动客户端一行代码）。
- 纯逻辑全在 `updater-core.js`，`node --test` 直接跑，不需要 Electron 环境。

## 12. 风险与边界（都写进 README，不藏）

1. **无签名**：`latest.yml` 的 sha512 保「完整」（防损坏、防错版），不保「来源」。
   HTTPS 是底线；纯 HTTP 仅限局域网自用，风险自担。这也是「先不签」的明确代价。
   签名校验的准确事实（2026-09-24 核 electron-updater 6.8.9 源码）：v6 在**下载时**
   校验（`NsisUpdater.doDownloadUpdate` 下完即调 `verifySignature`，不过关抛
   `ERR_UPDATER_INVALID_SIGNATURE`、清临时文件、不安装），且**仅当运行中 app 的
   `app-update.yml` 配了 `publisherName` 才校验**，没配则整体跳过。由此修正初稿的
   「未签名 → 签名的第一次更新可能被拒」：老用户跑的是没配 `publisherName` 的旧版，
   校验跳过，第一次签名更新装得上；真正的坑是**将来换证书**——新发布者与旧
   `publisherName` 不一致时旧版客户端会拒装，那才需要老用户手动重装。转签 / 换证书前
   按这两条各实测一次再写进结论。
2. **electron-updater × electron-builder 版本错配**：`latest.yml` 元数据格式随 builder
   大版本变（builder ≥27 默认新版 `files[]`；官方 compatibility 一节）。错配的表现是
   **构建全部成功、客户端永远检查不到更新且报错难懂**——又一种静默失效。当前锁
   `electron-builder ^25.1.8`（<27，旧版 `files[]` 格式），本条风险**暂不激活**；只有将来
   升级 builder 到 ≥27、或装了按新版格式读取的 electron-updater 时才需要重新对版。
   落地第 2 步的实跑结论（§13）与 §10 的「版本配对实跑」是常驻防线。
3. **URL 泄密面**：URL 会进 `updater.log` 与 package.json（若烘焙）。别放机密；
   要「路径即机密」就放随机串段，别放 token。
4. **portable 版没有自动更新**（官方 auto-updatable targets 只列 NSIS）。dist 同时产
   portable，README 要写明：便携版继续手工替换文件。
5. **杀软 / Defender**：由用户自己的应用进程启动的静默 NSIS 安装一般无感，但值得在冒烟时留意一次（§10 端到端冒烟各行）。
6. **v6/v7 的安装 API 分叉**（§3.1）：`autoInstallEvent`（v7）vs `autoInstallOnAppQuit`（v6）。
   2026-09-24 实核 npm dist-tags：`latest` = 6.8.9、v7 stable 不存在——本条当前**不激活**，
   按 v6 原生 `autoInstallOnAppQuit` 写；v7 出 stable 时只差一行切换（§3.1 末）。
   留下的教训是「不确认版本就写代码等于赌默认值」，所以 §13 第 2 步把核版本固化成动作。
