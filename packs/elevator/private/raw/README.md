# 原始资料待整理区

**这个目录引擎不读，也不会自动解析。** 放这里只是为了把"原始资料"和"喂给模型的结构化条目"
分开存放 —— 生成脚本时读的永远是上一层的 `products.yaml` / `service.yaml` / `cases.yaml` / `faq.yaml`。

⚠ 以前这里写着"丢进来跟我说一句就自动抽取写进 yaml"，**那个工作流没有实现**（引擎侧只有
只读的取文件接口），照着它等就不会有任何东西被抽出来。当前可行的做法：

```
① 把文件放进本目录（备查）
        ↓
② 把内容贴给你手边的任意 AI 助手，让它按上层 yaml 的字段结构整理成条目
        ↓
③ 粘进 ../products.yaml 等文件，**只填做得到、核实过的**
        ↓
④ 核对一遍。以后生成脚本自动使用，你不用再提
```

---

## 为什么要"整理成 yaml"这一步，不让模型直接读原始文件

每次生成都要把注入的知识拼进提示词（当前撰写一轮约 8~9k 字符）。

| 方式 | 每次进提示词的体量 |
|---|---|
| 整份 100 页产品手册 | 数万 token，且大部分是无用排版 |
| 整理后的 yaml 条目 | 几百到一两千字，全是有效字段 |

**原始文件 = 源码，yaml = 编译产物。** 编译一次，之后每次运行都轻量。资料更新时重新整理一次就行。

整理时的两条硬规矩（这两条都会被模型当成事实）：

- **不要留示例数字**。带"示例："字样的**字符串值**会被引擎剥离，但整条目级的示例（例如一条
  只有 `type: 加装` 的空壳案例）剔不掉，会照原样注入。没填的条目请整条删掉。
- **`source` / `verified` 只写真核实过的**。引擎不检查这两个字段，空着或编一个都会被引用；
  伪造的溯源章（"2026版产品手册"、某个假日期）曾真实出现在交付脚本里，那是合规问题不是排版问题。

## 命名建议（可选，方便日后管理）

```
raw/
├── 产品手册_2026版.pdf
├── 型号参数表.xlsx
├── 案例清单.xlsx
├── 服务承诺与报价规则.docx
└── 政策文件_加装电梯补助.pdf
```

按资料类型命名即可，不需要严格规范。

---

## 敏感信息处理

不需要的文件不要放进来。以下内容建议**不要**投放：

- 含客户联系方式的名单
- 含成本底价的报价表
- 竞品内部资料
- 未公开项目文件

**报价表的正确用法**：给我看可以，但我只会抽取**构成规则**（哪几部分、占比逻辑），不把具体底价写进知识库。
